You are working on `jaymemata-max/baby-name-swipe`, a Next.js 15 + Supabase
baby name swiping app for one couple. Read `AGENTS.md` first: it lists six
invariants that must not be broken, and the four checks that must pass before

Work on a branch named `codex/e2e-verification`. Do not push to `main` and do
not touch branches beginning with `claude/`. Another agent works in this repo.

## The problem

The backend is tested: `./scripts/test-schema.sh` runs four suites covering
the match trigger, row level security, undo and the couple rules, all
passing.

The frontend is not. The 15 components and 4 hooks typecheck, lint and build,
and the sign-in screen has been rendered in a real browser. **Every other
screen - the swipe deck, the match celebration, the matches list, add-name,
onboarding, settings - has never been driven with real data.** They were
generated by another model and then reworked by hand. Assume bugs.

Your job is to find those bugs and fix them.

## Approach, in priority order

### 1. Try for a real local stack

```bash
npx supabase init
npx supabase start
npx supabase db reset
```

If Docker is available in your environment this gives you real Postgres, real
GoTrue auth and real Realtime. Create two users, sign them in, and drive the
whole flow. This is the highest-fidelity option by a wide margin.

If Docker is not available, say so plainly in your final report and move to
step 2. Do not fake a backend to get past this. A previous attempt at this
project shipped a 755-line in-memory Express server standing in for the real
API, and everything built on top of it was worthless. `docs/DECISIONS.md`
has the detail.

### 2. Component tests against a mocked fetch layer

Install Vitest and React Testing Library. Mock `fetch`, not Supabase, and
assert on what the user sees. Cover at minimum:

- **Deck**: renders a card; swiping calls `POST /api/swipes` with the right
  body; the card leaves the stack optimistically; a failed request restores
  it and shows the error banner.
- **Match celebration**: fires when the response has `matched_now: true`,
  does **not** fire when `matched: true, matched_now: false`. This is
  invariant 3 in `AGENTS.md` and the single easiest thing to regress.
- **Undo**: `DELETE /api/swipes` puts the card back; a `404 nothing_to_undo`
  shows a message rather than failing silently.
- **Prefetch**: with the stack at 8 cards a second `GET /api/deck` fires, and
  the newly appended cards survive a swipe. There was a bug here where a
  captured array was written back to state and discarded prefetched cards;
  make sure it stays fixed.
- **Matches list**: renders matches, toggles `shortlisted`, saves a note,
  filters by gender, and shows an empty state with zero matches.
- **MatchDetailSheet**: opens, closes, and reopens on a *different* match -
  the note must update. This component previously called `useState` after an
  early return, which crashes React on close.
- **Onboarding**: create-a-couple shows the invite code; joining with a bad
  code shows the `404 invalid_invite_code` message; joining a full couple
  shows the `409 couple_full` message.
- **Add name**: `409 duplicate_name` is shown to the user.
- **Signed-out and no-couple gates**: a `401` routes to sign-in, a `couple:
  null` response routes to onboarding.

### 3. Playwright specs, whether or not you can run them

Write `e2e/` specs for the full two-person flow: sign in, create, join, both
swipe the same name, both see the match. Wire them to a local Supabase.
Commit them even if you cannot run them - they are what verifies the next
change. Say clearly in your report which ones you actually executed.

## Rules

- **Do not change the API contract.** `docs/API.md` is accurate and the UI is
  built against it. If you find a genuine backend bug, fix it in
  `src/app/api/` or a new migration, and update `docs/API.md` in the same
  commit.
- **Do not add an authentication bypass**, a demo login, or a "continue as"
  button, for testing or anything else. Tests get sessions the real way.
- **Do not add dependencies casually.** Test tooling as devDependencies is
  fine. Anything that ships to the browser needs a reason in the commit
  message; this runs on a free tier and the bundle is already 218 kB.
- **Do not edit applied migrations in place.** New file, later timestamp.
- Every fix needs a test that fails before it and passes after.

## Done looks like

- `npm run typecheck`, `npm run lint`, `npm run build` and
  `./scripts/test-schema.sh` all pass.
- `npm test` runs the new suite and passes.
- A branch pushed with one commit per logical fix, each message saying what
  was broken and how you found it.
- A final report that separates **what you verified by running it** from
  **what you only wrote tests for**. If you could not run something, say so.
  Do not describe untested code as working.
